## 概述

### 模塊定位

採購管理系統是 LinkWise 的業務核心，負責從採購申請 (PR) 的創建、批准、轉換為採購訂單 (PO) 到訂單狀態跟蹤的全生命週期管理。

### 支持的需求

| 需求編碼 | 功能分組 | 優先級 | 複雜度 |
|---------|--------|-------|-------|
| **FR-P1.1 ~ FR-P1.3** | PR 創建與管理 (創建、批量導入、查詢) | P0 | ⭐⭐ |
| **FR-P2.1 ~ FR-P2.4** | 批准工作流 (路由、操作、備註、狀態) | P0 | ⭐⭐⭐⭐ |
| **FR-P3.1 ~ FR-P3.2** | PR 轉 PO (手動轉換、自動轉換) | P0 | ⭐⭐⭐ |
| **FR-P4.1 ~ FR-P4.3** | PO 狀態管理 (查詢、跟蹤、確認) | P0 | ⭐⭐⭐ |

### 業務價值

- 📝 **採購流程自動化**: 標準化的 PR 申請和批准流程
- ⚡ **批准加速**: 自動批准規則減少手工處理
- 📊 **可視化控制**: 實時追蹤 PR/PO 狀態
- 💰 **成本控制**: 多層級批准、超預算告警

## 採購申請 (PR) 管理 (FR-P1.1 ~ FR-P1.3)

### FR-P1.1: 採購申請創建

**需求描述**: 支持創建採購申請 (手動、批量導入 Excel、API)

#### 手動創建 (常規流程)

**PR 表單結構**:

```
[基本信息] [商品明細] [附加選項]

基本信息:
├─ PR 編號: (自動生成)
├─ 申請人: (自動填充)
├─ 申請部門: (自動填充)
├─ 申請日期: (自動填充)
├─ 預期交付日期: (必填)
├─ 成本中心: (必填，用於財務分配)
└─ 備註: (可選)

商品明細 (表格):
├─ 商品代碼: (必填，可下拉搜索)
├─ 商品名稱: (自動填充)
├─ 規格: (自動填充)
├─ 單位: (自動填充)
├─ 數量: (必填，正整數)
├─ 單位價格: (可能自動帶出歷史價格)
├─ 需求日期: (默認同申請日期)
└─ 備註: (可選)

[+ 添加行] [清除]

預估金額: (自動計算)

附加選項:
├─ 緊急等級: (普通 / 加急 / 極急)
├─ 相關項目: (多選)
└─ 優先供應商: (可選)
```

**商品代碼搜索**:
```
搜索條件:
- 商品代碼
- 商品名稱
- 商品分類

返回結果:
| 代碼 | 名稱 | 規格 | 單位 | 最低訂購量 |
|-----|------|------|------|----------|
| SKU001 | 原材料 A | 10kg | 袋 | 5 |
```

**表單驗證**:
```
- 數量 > 0
- 單位價格 > 0
- 預期交付日期 >= 今天
- 至少包含 1 行商品
```

**保存**:
```
提交時:
1. 驗證表單
2. 計算預估金額
3. 生成 PR 編號: PR-{YYYYMM}-{SEQ}
4. 保存為草稿或直接提交
5. 觸發批准流程
```

[表格顯示失敗原因]

## 批准工作流 (FR-P2.1 ~ FR-P2.4)

### FR-P2.1: 批准路由規則

**需求描述**: 根據 PR 特性自動路由至合適的批准者

**批准規則引擎**:

```
規則 1: 金額規則
IF 金額 <= ¥10K THEN 路由至直屬主管
IF 金額 > ¥10K AND 金額 <= ¥50K THEN 路由至部門經理
IF 金額 > ¥50K AND 金額 <= ¥200K THEN 路由至副總
IF 金額 > ¥200K THEN 路由至總經理 + 財務總監

規則 2: 特殊商品規則
IF 商品分類 == "IT 設備" THEN 添加 CTO 作為批准者
IF 商品分類 == "法律服務" THEN 添加法律顧問作為批准者

規則 3: 部門規則
IF 申請部門 == "市場部" THEN 添加市場總監作為批准者

規則 4: 緊急規則
IF 緊急等級 == "極急" THEN 縮短批准期限至 4 小時
IF 緊急等級 == "加急" THEN 批准期限 24 小時

批准路由結果:
[批准步驟 1] → [批准步驟 2] → [完成]
    |              |
 主管        部門經理
```

**配置界面** (管理員):
```
批准規則管理:
├─ 規則 1: 金額 <= 10K → 主管
├─ 規則 2: 金額 > 10K → 經理
├─ ...

支持:
- 新增規則
- 編輯規則
- 刪除規則
- 調整優先級 (優先級高的先執行)
```

### FR-P3.2: 自動轉換規則 (可選，P1)

**需求描述**: 定義自動轉換規則，自動將符合條件的 PR 轉為 PO

**自動轉換規則**:

```
規則 1: 重複採購
IF 商品 在過去 6 個月內採購過
   AND 供應商信用良好 (評分 >= 80)
   AND 金額 <= ¥10K
THEN 自動轉換為 PO (使用上次供應商)

規則 2: 預設供應商
IF 商品有預設供應商
   AND 預設供應商狀態為活躍
THEN 自動轉換為 PO (使用預設供應商)

規則 3: 合同采購
IF 商品屬於已簽訂框架協議的類別
   AND 框架協議有效
THEN 自動轉換為 PO (按合同條款)

自動轉換觸發:
- 後台定時任務 (每小時檢查一次)
- 管理員手動觸發
- PR 批准完成後自動檢查
```

**配置界面**:
```
自動轉換規則管理:
├─ 規則 1: 重複採購 [啟用/禁用] [編輯]
├─ 規則 2: 預設供應商 [啟用/禁用] [編輯]
└─ 規則 3: 合同采購 [啟用/禁用] [編輯]

日誌:
2026-05-08 10:00 | PR-202605-001 自動轉換為 PO (規則 1)
```

## PO 狀態管理 (FR-P4.1 ~ FR-P4.3)

### FR-P4.1: PO 查詢與狀態追蹤

**需求描述**: 查詢 PO 並實時追蹤狀態

**PO 列表**:

```
篩選:
├─ 時間範圍
├─ 狀態: 已發送 / 已確認 / 備貨中 / 已發貨 / 已交付 / 已結案
├─ 供應商
├─ 金額範圍

搜索: PO 編號 / 商品名稱

排序: 建立日期 / 交期 / 金額

列表顯示:
| PO 編號 | 供應商 | 金額 | 狀態 | 交期 | 操作 |
|--------|-------|------|------|------|------|
| PO-202605-0001 | 廠商 A | ¥150K | 已發貨 | 2026-05-15 | 查看 |
```

**狀態流**:
```
已發送 → 已確認 → 備貨中 → 已發貨 → 已交付 → 已結案

狀態定義:
已發送:   PO 發送給供應商，待供應商確認
已確認:   供應商已確認 PO，開始備貨
備貨中:   供應商正在準備貨物
已發貨:   貨物已從供應商發出，在途中
已交付:   貨物已收到指定地址
已結案:   PO 完全完成，開票付款

超期告警:
IF 當前日期 > 預期交期
THEN 標記為 "超期" (紅色)
   + 發送提醒給相關人
```

## 自動批准規則

### 實現邏輯

```java
@Service
public class ApprovalRoutingService {
    
    @Autowired
    private ApprovalRuleRepository ruleRepository;
    
    public List<Approver> routeForApproval(PurchaseRequest pr) {
        List<ApprovalRule> rules = ruleRepository.findByOrderByPriority();
        List<Approver> approvers = new ArrayList<>();
        
        for (ApprovalRule rule : rules) {
            if (rule.matches(pr)) {
                approvers.addAll(rule.getApprovers());
            }
        }
        
        return approvers;
    }
}
```

## 設計決策

### 決策 1: 為什麼分離批准步驟而不是單一決策？

**理由**: 不同金額需要不同層級的批准，確保風險控制的有效性。

### 決策 2: 為什麼支持 PR 批準後修改？

**理由**: 採購過程中常見供應商庫存變化，允許修改提高流程靈活性。

### 決策 3: 為什麼使用 Saga 模式進行 PR 轉 PO？

**理由**: 涉及多個操作 (創建 PO、更新 PR 狀態、發郵件)，Saga 模式確保一致性。
