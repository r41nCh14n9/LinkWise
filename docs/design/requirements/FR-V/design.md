## 概述

### 模塊定位

VMS (Vendor Management System) 是 LinkWise 的核心業務模塊，負責供應商的全生命週期管理、風險評估、績效監控和 Onboarding 流程。

### 支持的需求

| 需求編碼 | 功能分組 | 優先級 | 複雜度 |
|---------|--------|-------|-------|
| **FR-V1.1 ~ FR-V1.3** | 供應商檔案管理 (列表、詳情、版本控制) | P0 | ⭐⭐ |
| **FR-V2.1 ~ FR-V2.3** | 風險評級系統 (計算、預警、詳情) | P0 | ⭐⭐⭐⭐ |
| **FR-V3.1 ~ FR-V3.2** | 績效追蹤 (看板、歷史) | P0 | ⭐⭐⭐ |
| **FR-V4.1 ~ FR-V4.2** | Onboarding 流程 (清單、風險控制) | P0 | ⭐⭐⭐ |

### 業務價值

- 🤝 **供應商管理**: 完整的生命週期管理
- 🚨 **風險控制**: 4 維度評分 + 實時預警
- 📊 **績效監控**: 多個 KPI 的實時追蹤
- ✅ **Onboarding**: 結構化的合作流程

## 風險評級系統 (FR-V2.1 ~ FR-V2.3)

### FR-V2.1: 實時風險評級計算 (4 維度)

**需求描述**: 實時計算供應商綜合評分 (財務、交付、質量、合規)

**評分維度**:

#### 1. 財務健康度 (40%)
```
指標:
- 應付賬款逾期天數: 越短越好
- 應付賬款比例: 相對於合作金額
- 破產風險指示: 基於公開信息

評分規則:
- 無逾期: 100 分
- 1-30 天逾期: 80 分
- 31-60 天逾期: 60 分
- 60+ 天逾期: 40 分
```

#### 2. 交付能力 (30%)
```
指標:
- 準時交付率 (%) = 按時交付訂單 / 總訂單
- 延遲平均天數
- 發貨完成率

評分規則:
- 準時率 >= 95%: 100 分
- 準時率 90-95%: 85 分
- 準時率 85-90%: 70 分
- 準時率 < 85%: 50 分
```

#### 3. 質量表現 (20%)
```
指標:
- 缺陷率 (%) = 有缺陷訂單 / 總訂單
- 退貨率 (%)
- 質量投訴次數

評分規則:
- 缺陷率 < 1%: 100 分
- 缺陷率 1-3%: 80 分
- 缺陷率 3-5%: 60 分
- 缺陷率 > 5%: 40 分
```

#### 4. 合規狀態 (10%)
```
指標:
- 資質證書有效期
- 法律糾紛情況
- 行政處罰情況

評分規則:
- 所有資質有效: 100 分
- 有資質即將到期: 80 分
- 有過期資質: 60 分
- 有法律糾紛: 40 分
- 有行政處罰: 0 分
```

**計算公式**:
```
綜合評分 = 
  (財務得分 × 40% +
   交付得分 × 30% +
   質量得分 × 20% +
   合規得分 × 10%) / 100

範圍: 0-100
```

**風險等級**:
```
綠色 (Green):   85-100 分 (低風險)
黃色 (Yellow):  70-84 分  (中風險)
紅色 (Red):     <70 分    (高風險)
```

**涉及表**: 
- vendor
- vendor_score
- purchase_order (用於計算準時率)
- vendor_defect (缺陷記錄)
- vendor_complaint (投訴記錄)

### FR-V2.2: 風險預警規則

**需求描述**: 風險預警規則 (綠/黃/紅 狀態、告警)

**自動告警**:
```
1. 評分下降告警
   IF 本週評分 < 上週評分 - 5 分
   THEN 發送告警: "供應商評分下降"

2. 轉入黃色告警
   IF 評分進入黃色區間 (70-84)
   THEN 發送告警: "供應商風險升級為中等"

3. 轉入紅色告警
   IF 評分進入紅色區間 (<70)
   THEN 發送告警: "供應商風險升級為高風險"
   + 通知採購部經理

4. 缺陷率告警
   IF 本月缺陷率 > 5%
   THEN 發送告警: "供應商缺陷率異常"

5. 準時率告警
   IF 準時交付率 < 90% (最近 30 天)
   THEN 發送告警: "供應商交付能力下降"
```

**實現**:
```java
@Scheduled(fixedDelay = 300000)  // 每 5 分鐘檢查
public void checkVendorRiskAlerts() {
    List<Vendor> vendors = vendorRepository.findAll();
    
    vendors.forEach(vendor -> {
        VendorScore latestScore = calculateVendorScore(vendor);
        VendorScore previousScore = getPreviousScore(vendor);
        
        // 檢查評分變化
        if (latestScore.getScore() < previousScore.getScore() - 5) {
            sendAlert(vendor, AlertType.SCORE_DROPPED);
        }
        
        // 檢查風險等級變化
        if (getRiskLevel(latestScore) > getRiskLevel(previousScore)) {
            sendAlert(vendor, AlertType.RISK_UPGRADED);
        }
    });
}
```

### FR-V4.2: Onboarding 風險控制 (P1, 初期可選)

**需求描述**: Onboarding 風險控制 (進度追蹤、失敗重試)

**風險識別**:
```
1. 過期風險
   IF Onboarding 已進行 30 天未完成
   THEN 標記為 "風險：進度緩慢"
   + 發送提醒郵件

2. 文件風險
   IF 上傳文件驗證失敗 3 次
   THEN 標記為 "需人工審查"
   + 通知管理員

3. 銀行風險
   IF 銀行帳戶驗證失敗 2 次
   THEN 標記為 "需人工驗證"
   + 要求供應商提供其他證明

4. 質量風險
   IF 試單質量不合格
   THEN 要求供應商改善
   + 延遲 Onboarding 完成
```

**失敗重試**:
```
失敗場景:
- 文件上傳失敗 → 允許重新上傳
- 銀行驗證失敗 → 允許重新驗證
- 試單質量不合格 → 允許重新下單

重試限制:
- 最多 3 次重試
- 超過 3 次 → 需管理員介入
```

## 安全設計

### 多租戶隔離

```
- 所有供應商查詢都過濾 organization_id
- 供應商與組織的關聯驗證
- 不同企業的供應商不能混淆
```

### 權限控制

```
Admin:       查看、編輯、刪除所有供應商
VMS Manager: 查看、編輯分配的供應商
Buyer:       查看供應商信息、查詢價格
```

## 設計決策

### 決策: 為什麼使用 4 維度評分而不是簡單平均？

**理由**: 不同維度對供應商風險影響不同，財務風險最嚴重，需要權重最高。
